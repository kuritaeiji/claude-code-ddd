# 実装ワークフロー: $ARGUMENTS

以下の 6 ステップを順番に実行してください。ステップをスキップしてはいけません。

---

## ステップ 1: プロジェクト理解

Read ツールで docs/ 配下のドキュメントをすべて読み、ドメイン・アーキテクチャ・ユースケースを完全に把握してください。

- docs/production-requirements.md
- docs/domain.md
- docs/usecase.md
- docs/schema.md（存在しない場合はスキップ）
- docs/architecture.md
- docs/repository-structure.md

---

## ステップ 2: 既存パターン調査

Bash ツールまたは Grep で backend/ 配下の既存コードを調査し、以下のパターンを把握してください。
まだコードが存在しない場合はスキップしてください。

- エンティティ・値オブジェクトの実装パターン（ファイル構成・命名規則）
- リポジトリインターフェースの定義パターン
- ユースケース（コマンド・クエリ）の実装パターン
- コントローラーの実装パターン（ルーティング・エラーハンドリング）
- テストの実装パターン（ファイル配置・テストヘルパー）

---

## ステップ 3: 計画フェーズ

Bash ツールで `date +%Y%m%d` を実行して今日の日付を取得し、
`.steering/<YYYYMMDD>-$ARGUMENTS/` ディレクトリを作成してください。
次に以下の 3 ファイルを Write ツールで作成してください。

### requirements.md（要件）

- 実装対象の機能・ユースケース一覧と対応 API エンドポイント
- ビジネスルール・バリデーション制約（domain.md から抜粋）
- 関連するドメインイベントと副作用

### approach.md（実装方針）

- アーキテクチャ層ごとの実装方針
- 新規作成ファイル一覧（相対パス付き）
- 変更ファイル一覧（相対パス付き）
- テスト方針（何をどのレイヤーでテストするか）
- ドキュメント変更計画: 実装に伴い更新が必要な `docs/` 配下のファイルと、各ファイルへの変更内容を列挙する（変更不要な場合は「なし」と明記）

### tasks.md（タスクリスト）

- 実装タスクを `[ ]` 形式でリストアップ
- 1 タスク = 1 ファイルまたは 1 機能単位（細かく分割する）
- 依存関係順に並べる（ドメイン層 → インフラ層 → ユースケース層 → コントローラー層）
- テストも各レイヤーのタスクに含める
- ドキュメント更新タスクも含める: approach.md の「ドキュメント変更計画」に基づき、変更が必要な docs/ ファイルをタスクに追加する（コード実装タスクの後に並べる）

## ステップ 4: 実装ループ

`.steering/<YYYYMMDD>-$ARGUMENTS/tasks.md` の **すべてのタスクが `[x]` になるまで** 以下を繰り返してください。

1. tasks.md を Read ツールで読み、最初の `[ ]` タスクを特定する
2. そのタスクを実装する（Write / Edit ツールでコードを書く）
3. tasks.md の該当行を `[ ]` → `[x]` に Edit ツールで更新する

**実装の制約:**

- オニオンアーキテクチャの依存方向を守る（Domain ← Usecase ← Controller、Domain ← Infrastructure）
- ビジネスルール・バリデーションはドメイン層のみに実装する
- CQRS のクエリはドメインモデルを経由せず、専用 DTO で PostgreSQL から直接読み取る
- コメントは Why が非自明な場合のみ書く。What コメントは書かない

サブエージェントへのプロンプトには以下を必ず含めてください。

- `.claude/skills/review-code/SKILL.md` を最初に Read し、その手順・観点・出力形式に従ってレビューを実行する

- 重大な問題は具体的に列挙し、ファイルパスと行番号付きで修正案を提示する

レビュー結果に問題があれば修正してください。

approach.md の「ドキュメント変更計画」に変更ファイルが 1 つ以上ある場合のみ実行してください。変更がない場合はこのステップをスキップしてください。

## ステップ 7: テスト実行

Agent ツールでサブエージェントを起動し、以下のコマンドを実行してテスト結果を報告させてください。

```bash
cd /home/kuritaeiji/claude-code/backend && make test
```

サブエージェントへのプロンプトには以下を含めてください。

- 上記コマンドを実行する
- テストの成否（PASS / FAIL）を報告する
- 失敗したテストがあればテスト名・エラーメッセージ・ファイルパスと行番号をすべて列挙する

テストが失敗した場合は原因を調査して修正し、再度 Agent ツールでサブエージェントを起動して同じコマンドを実行し、すべてのテストがパスするまで繰り返してください。

## ステップ 8: コミットメッセージ出力

テストがすべてパスしたら、今回の実装内容をコミットするためのコミットメッセージを生成し、ユーザーに提示してください。
**コミットの実行はしません。メッセージを出力するだけです。**

### 形式

```
<type>/<簡潔なタイトル>

<本文: なぜこの変更が必要だったか>

<本文: 何を変更したか（主要な追加・変更ファイル単位で箇条書き）>
```

### type の選び方（先頭プレフィックス）

- `feat/` — 新機能の追加
- `fix/` — バグ修正
- `refactor/` — 振る舞いを変えないリファクタリング
- `test/` — テストのみの追加・修正
- `docs/` — ドキュメントのみの変更
- `chore/` — ビルド・依存関係・設定など補助的な変更

### 内容の指針

- **タイトル**: 50 文字以内、命令形ではなく体言止め・現在形で簡潔に
- **本文（なぜ）**: ビジネス上の動機・ドメイン上の必要性・解決したい課題を 1〜3 文で書く（`.steering/<YYYYMMDD>-$ARGUMENTS/requirements.md` を参考にする）
- **本文（何を）**: アーキテクチャ層ごとに「どのファイルに何を追加・変更したか」を箇条書きで書く（`.steering/<YYYYMMDD>-$ARGUMENTS/approach.md` を参考にする）

### 出力方法

メッセージはコードブロック（```）で囲んで出力し、ユーザーがそのままコピーして `git commit` に使えるようにしてください。
